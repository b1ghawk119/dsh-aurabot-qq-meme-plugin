# 在 Docker 中使用表情制作

**1.3.5 已通过 Debian 12 容器测试：x86_64 原生执行，ARM64 使用 QEMU 仿真。** 基础库和可选扩展均可生成表情，不需要显卡或桌面环境。

这次测试的是表情模块及其生成进程，没有启动 DSH、NapCat 或 SnowLuma，也没有实际发送 QQ 消息。DSH 本身的容器部署请按其官方说明操作；此处补充表情模块的环境要求。

## 看到“缺少必要组件”时怎么处理

把本节交给部署机器人的人：在 Docker 镜像中补齐下面的组件，重新启动容器，再点击 **重试准备** 或 **安装扩展库**。已有素材不需要删除。普通 Linux 安装可通过系统包管理器安装同名组件。

1.3.6 会在下载前检查这些条件；扩展检查不通过时，基础库仍可使用。面板不显示底层报错，具体缺少的组件记在模块日志中。

推荐使用 Debian/Ubuntu 系的 DSH 镜像。已验证的基础镜像为 `node:22-bookworm-slim`，Node 22.23.5；不适用于 Alpine，也未适配 32 位 ARM。

在 Dockerfile 中补充：

```dockerfile
RUN apt-get update \
 && apt-get install -y --no-install-recommends \
      curl ca-certificates tar \
      libfontconfig1 libglib2.0-0 libgomp1 libgl1 libegl1 \
 && rm -rf /var/lib/apt/lists/*
```

基础库需要字体相关系统库；可选扩展还需要图像处理相关系统库。精简镜像缺少 `libEGL.so.1` 时，扩展无法启动。Python 不需要用户手动安装，由模块的扩展安装流程准备。

以上命令用于 Debian 12；其他发行版的包名可能不同。修改镜像时保留原 DSH 的启动命令和运行用户。

## 数据目录要保留，也要能写入

将 DSH 实际使用的 `plugins-data/aurabot` 目录放在持久卷中，保留模块、配置和 `modules-data/meme` 内的资源。运行 DSH 的用户应能读写它，避免容器重建后重新下载。

已经安装好的模块代码可以只读；通过市场安装或升级时，模块目录必须可写。两种架构都已用 UID 1000 验证运行，不需要特权容器。

首次安装需要访问下载源。准备完成后，表情合成可以断网运行；实际 QQ 收发、获取头像或聊天图片仍需网络。不要把 Windows 的解释器或动态库复制到 Linux 容器中使用。

## 面板不能只靠端口映射

模块的模板列表、预览及扩展管理接口保留“只允许本机访问”的保护。Docker 网桥转发的请求不是回环请求，因此**直接映射后台端口可能收到拒绝访问**。

远端管理建议使用带认证、与 DSH 在同一容器或共享网络空间的反向代理，让代理访问容器内的 `127.0.0.1`：

```text
浏览器 → 带认证的反向代理 → 127.0.0.1 上的 DSH / AuraBot
         与 DSH 共享网络空间                  └─ 表情模块
```

同时遵守 DSH / AuraBot 本身的域名、登录及远端管理要求。不要删除模块的访问保护，也不要把后台 API 直接暴露到公网。测试中，直接端口映射被拒绝；鉴权代理拒绝未登录请求，允许已认证请求读取模板列表。

## 本次验证了什么

| 项目 | x86_64 | ARM64（仿真） |
|---|---|---|
| 加载基础库 / 加载扩展后 | 732 / 1005 | 732 / 1005 |
| 诺基亚：基础引擎、像素字体 | 通过 | 通过 |
| 宁宁举牌：附加基础模板库 | 通过 | 通过 |
| 小强举牌：可选扩展、GIF | 通过 | 通过 |
| 卸载扩展保留资源、再次启用 | 通过 | 通过 |
| 普通用户权限、断网生成 | 通过 | 通过 |

每种架构只选上述三个代表模板，没有遍历渲染整个模板库。生成图片已检查。

为节省磁盘，测试复用了已有的跨平台素材；两种架构的 Linux 运行组件和 Python 依赖均重新安装。**没有重测全部素材的首次下载，也没有做完整 DSH 与 QQ 网关联调。** ARM64 仿真结果证明这些组件能执行，不代表 ARM 真机的速度。

机器可读结果见 [docker-1.3.5.json](verification/docker-1.3.5.json)。以上生成测试使用 1.3.5；1.3.6 增加安装前检查，没有改动生成引擎与模板。
